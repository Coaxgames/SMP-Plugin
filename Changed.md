## Repository Push Rules

- Nobody pushes directly to `main`, owners included. Every commit on `main` must come from a merged PR.
- Push changes to the shared `UnStable` branch. Each push to `UnStable` builds that commit and creates or updates the single `UnStable` → `main` PR. Pushes to any other branch (for example `Stable-NoUpdates`) do not create a PR or a release; keep "do not PR" snapshots there.
- Merging that PR runs the release workflow: it builds the merged commit and publishes a GitHub Release with the plugin jar, the versioned resource-pack ZIP, its `.zip.sha1` sidecar and GitHub-generated notes. The tag and title are the same `major.minor.patch` version.
- Nobody edits the version by hand. The release workflow takes the highest of `main`'s version and the existing tags, adds one to the patch number, commits it to `build.gradle` and `plugin.yml` on `main` as `chore: release X.Y.Z` and tags that commit. Because of this, local branches show an older version than `main` (for example 2.22.8 locally vs 2.22.18).
- `main` needs two approving reviews from people other than the PR author. The repository owner may merge a PR without the approvals (bypass for pull requests only); the release workflow re-verifies two approvals for every other merge. Automatic PRs are authored by the bot, so any two collaborators can approve them.
- Fork contributors open the PR themselves. The plugin's auto-updater and resource-pack sender follow the newest GitHub Release, so a merged PR is what ships to the server.
- Repository branch protection and Actions permissions were documented but not configured by these code changes. The required settings are described in `.github/RELEASE-AUTOMATION.md`.
